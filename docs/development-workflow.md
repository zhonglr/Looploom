# Looploom 需求到落地流程规范

本文定义 Looploom 从需求提出到代码落地、发布和收尾的通用工作流，适用于前端、后端以及跨端改动。

本文规范的是协作流程、交付物和质量门禁，不规定后端必须使用何种语言、框架或目录结构。具体技术要求由对应领域的独立规范定义：

- 前端 TypeScript、React、组件和 CSS：[`frontend/coding-standards.md`](frontend/coding-standards.md)
- 后端技术规范：在后端代码建立后另行创建，不沿用前端规范

## 1. 流程总览

每项非临时性工作都应经过以下阶段：

```text
需求提出
  ↓
需求澄清与验收标准
  ↓
现状调查与影响分析
  ↓
方案设计与风险评估
  ↓
实施计划
  ↓
编码与增量验证
  ↓
集成验证与 Code Review
  ↓
发布、监控与回滚准备
  ↓
验收、记录与收尾
```

小型改动可以合并阶段，但不能跳过目标、验收标准、验证和收尾。高风险改动必须保留完整记录。

每个阶段结束时都要有明确的输出和继续条件。没有满足继续条件时，应停留在当前阶段，而不是用编码掩盖需求或方案的不确定性。

## 2. 角色与责任

一个人可以承担多个角色，但每项工作必须明确以下责任：

| 角色 | 责任 |
| --- | --- |
| 需求提出者 | 说明问题、目标、用户和优先级，参与验收 |
| 交付负责人 | 维护范围、计划、风险、依赖和最终状态 |
| 方案负责人 | 组织调查，记录技术方案和关键决策 |
| 实施者 | 按方案完成代码、测试、文档和迁移 |
| 评审者 | 独立检查正确性、风险、兼容性和可维护性 |
| 验收者 | 按验收标准确认用户可见结果 |
| 发布负责人 | 确认发布窗口、监控、回滚和沟通 |

不要求每个角色都是不同的人，但不能默认“写完代码的人自动完成所有验收”。

## 3. 需求阶段：先定义要解决的问题

### 3.1 需求必须回答的问题

开始实施前，需求至少应说明：

- 背景：为什么现在需要处理；
- 问题：当前具体什么行为、成本或风险不符合预期；
- 目标：完成后要改变什么；
- 用户和使用场景：谁在什么情况下使用；
- 范围：本次明确包含什么；
- 非目标：本次明确不处理什么；
- 约束：时间、兼容性、数据、安全、性能或依赖限制；
- 优先级：为什么现在做；
- 验收标准：如何客观判断完成。

“优化一下”“做得更好”“支持后端”这类描述不能直接作为实施任务，必须转换为可观察的结果。

### 3.2 验收标准

验收标准应描述行为和结果，而不是描述实现方式。优先使用 Given/When/Then：

```text
Given 用户已打开编辑器并选中一个节点
When 用户执行删除操作并确认
Then 节点从当前文档移除，Undo 可恢复该操作，刷新后结果仍然存在
```

验收标准应尽量覆盖：

- 正常路径；
- 空数据和边界条件；
- 失败和拒绝路径；
- 权限或身份差异；
- 刷新、重试、重复提交或并发场景；
- 数据迁移和兼容性；
- 适用时的可访问性、性能和可观测性。

### 3.3 需求就绪条件（Definition of Ready）

需求满足以下条件后才进入调查或实施：

- 目标和非目标明确；
- 受影响的用户或系统明确；
- 验收标准可验证；
- 关键术语有统一含义；
- 已知依赖和限制已记录；
- 未解决的问题已经指定负责人和截止时间；
- 交付负责人和验收者已明确。

如果需求仍存在会改变方案或范围的关键歧义，应先澄清，不得自行假设后扩大实现范围。

## 4. 调查阶段：建立事实和影响范围

### 4.1 调查内容

方案设计前应检查：

- 当前实现和实际用户行为；
- 相关应用、共享包和服务；
- 数据模型、接口、协议和持久化边界；
- 状态 owner、生命周期和错误处理；
- 现有测试、监控和发布方式；
- 依赖版本、兼容性和迁移要求；
- 可能受影响的其他功能和团队。

调查应以代码、测试、运行结果和已有文档为证据。不要只根据文件名、旧注释或个人记忆判断影响范围。

### 4.2 影响地图

至少记录以下影响：

```text
需求
├─ 用户界面或交互
├─ 业务规则和状态
├─ 前后端接口或消息协议
├─ 数据库/文件/缓存/持久化
├─ 权限与安全
├─ 测试与验收
├─ 监控、日志与告警
└─ 发布与回滚
```

不受影响的分支也应明确写出原因，防止后续重复调查。

### 4.3 调查输出

调查结束后应形成简短记录，包含：

- 已确认事实；
- 相关代码和文档位置；
- 受影响边界；
- 关键假设；
- 待确认问题；
- 风险和建议方案。

如果调查发现需求本身不成立、现有架构无法安全支持，或需要改变范围，应返回需求阶段重新确认。

## 5. 设计阶段：先确定边界，再确定实现

### 5.1 方案必须说明的内容

方案记录至少包括：

- 目标和范围；
- 模块边界与依赖方向；
- 数据和状态的唯一 owner；
- 输入、输出和失败结果；
- 前后端或模块间的接口/协议变化；
- 兼容策略和迁移顺序；
- 权限、隐私和安全边界；
- 性能和容量假设；
- 日志、指标、追踪和告警；
- 测试分层与验收方式；
- 发布和回滚方案。

方案应优先复用已有稳定边界。为了一个单一用例，不应提前建立无法验证的通用框架、抽象层或扩展点。

### 5.2 跨端契约

涉及前后端或多个 workspace 包时，应先定义契约，再并行实施。契约至少包含：

- 请求或消息的输入结构；
- 成功结果；
- 业务拒绝和程序异常；
- 版本或 revision 规则；
- 超时、重试和幂等行为；
- 权限和敏感字段；
- 向后兼容和迁移策略。

契约变化必须说明消费者、发布顺序和旧版本行为。不能只修改一端后等待另一端“适配”。

### 5.3 关键决策记录

当存在多个合理方案，或决策会影响长期结构、数据格式、接口兼容性、依赖选型或运维方式时，应记录 ADR 或等价决策记录：

- 背景和问题；
- 备选方案；
- 选择的方案；
- 选择原因和取舍；
- 被放弃方案；
- 未来重新评估的条件。

## 6. 计划阶段：把方案变成可验证的工作包

### 6.1 任务拆分

任务应按可独立验证的结果拆分，而不是按文件数量拆分。每个任务应说明：

- 预期结果；
- 前置依赖；
- 影响边界；
- 验证方式；
- 是否包含迁移、文档、监控或发布配置；
- 完成后由谁验收。

推荐顺序：

```text
契约/模型
  → Domain 或服务规则
  → Integration / Adapter
  → UI 或调用方
  → 测试与观测
  → 迁移、发布和文档
```

具体顺序可以因项目调整，但每个依赖必须明确，不应让多个分支通过隐含约定连接。

### 6.2 风险分级

| 级别 | 典型改动 | 最低要求 |
| --- | --- | --- |
| 低 | 文案、局部样式、无行为变化的重构 | 自测、必要的静态检查 |
| 中 | 新交互、共享包、接口消费者、状态变化 | 测试、Code Review、验收 |
| 高 | 数据迁移、权限、协议破坏性变化、核心流程、不可逆发布 | 方案记录、专项评审、回滚演练或明确替代方案、上线监控 |

风险等级由影响范围和失败代价决定，不由代码行数决定。

### 6.3 计划就绪条件

进入编码前必须具备：

- 已确认的需求和验收标准；
- 可执行的方案或已记录的轻量决策；
- 清晰的任务顺序和依赖；
- 已知风险、迁移和回滚方案；
- 每个任务的验证方式；
- 对应领域规范的入口。

## 7. 实施阶段：小步提交，持续验证

### 7.1 编码原则

- 先建立边界和契约，再填充实现；
- 每次改动保持单一主题，避免把无关重构混入功能；
- 不为未来假设添加未验证的抽象；
- 不通过删除测试、放宽类型、吞掉错误或硬编码结果来“通过”验证；
- 外部输入、权限、失败和重试路径与正常路径同等对待；
- 代码改变行为时同步更新测试、文档、日志、指标和配置；
- 迁移必须考虑旧数据、旧消费者和失败后的恢复方式。

### 7.2 增量验证

每完成一个可验证工作包，都应立即执行对应检查：

- 类型、格式和静态检查；
- 领域或服务单元测试；
- 模块集成或契约测试；
- 受影响的应用构建；
- 需要时的浏览器或端到端测试。

不要等所有代码完成后才第一次运行验证。失败时记录失败原因和修复结果，避免在最后阶段集中处理未知问题。

### 7.3 领域规范的适用方式

实施时只应用受影响领域的技术规范：

- 前端改动遵循 [`frontend/coding-standards.md`](frontend/coding-standards.md)；
- 后端改动遵循后端独立规范；
- 跨端改动同时满足双方规范，并额外满足本文件的接口、兼容性、发布和验收要求。

前端规范不得被当作后端规范的替代品，后端规范也不得未经评估直接复制到前端。

## 8. 验证阶段：证明结果而不是证明代码存在

### 8.1 验证分层

| 层级 | 证明内容 |
| --- | --- |
| 静态检查 | 类型、格式、危险模式和依赖边界 |
| 单元测试 | 纯规则、转换、边界和错误结果 |
| 模块集成测试 | 模块之间的真实协作和生命周期 |
| 契约测试 | 生产者与消费者对接口/消息的共同理解 |
| 应用测试 | 应用启动、构建和关键流程 |
| E2E/浏览器测试 | 用户可见行为、跨系统流程和真实运行环境 |
| 人工验收 | 需求中的体验、业务语义和非自动化条件 |

不是所有改动都需要所有层级，但跳过某层必须有理由。验证范围应随风险等级扩大。

### 8.2 验收记录

验收应逐条对应需求中的验收标准，并记录：

- 通过/未通过；
- 使用的环境和版本；
- 测试或操作步骤；
- 已知限制；
- 未完成事项及后续负责人。

“构建通过”只说明代码可构建，不等于需求已验收。

## 9. Code Review 阶段

### 9.1 提交评审前

提交者必须先完成自查：

- 改动是否完全覆盖范围内的验收标准；
- 是否有越界改动或未记录的行为变化；
- 是否保留了兼容性、错误处理和权限检查；
- 测试是否验证失败和边界路径；
- 是否更新了相关文档、配置、迁移和监控；
- 是否执行了与风险匹配的验证；
- 是否说明了已知限制和未解决问题。

### 9.2 评审顺序

评审优先级如下：

1. 正确性和验收标准；
2. 数据安全、权限和隐私；
3. 兼容性、迁移和回滚；
4. 状态、并发、资源清理和错误处理；
5. 测试和可观测性；
6. 结构、可维护性和风格。

评审意见应指出问题、影响和建议方向，不以个人偏好替代项目规范。未解决的高风险意见不能通过“以后再改”关闭，除非已建立明确的后续任务、负责人和截止时间。

## 10. 发布阶段：让变化可控

发布前确认：

- 所有阻断性验收标准通过；
- 代码、配置、数据迁移和依赖顺序明确；
- 回滚方式已验证或已明确不可回滚时的补救方案；
- 监控、日志、指标和告警已就绪；
- 高风险改动具备灰度、Feature Flag 或分阶段启用方案；
- 相关人员知道发布时间、影响范围和异常联系人；
- 用户可见变化有必要的说明。

发布顺序必须遵循兼容策略。例如先发布兼容的新生产者，再发布消费者，最后移除旧路径；不能让短暂的部署中间态产生不可恢复的数据或协议错误。

## 11. 发布后与收尾

发布后应在约定窗口内检查：

- 核心流程成功率和错误率；
- 延迟、资源使用和容量；
- 数据迁移结果；
- 用户反馈和支持请求；
- 日志、指标和告警是否与预期一致。

工作只有在以下事项完成后才算真正结束：

- 验收记录已完成；
- 文档、示例和变更说明已更新；
- 临时 Feature Flag、兼容分支、迁移脚本或调试配置已清理或转为正式维护项；
- 未完成事项已拆成后续任务；
- 关键决策和已知限制已记录；
- 高风险改动完成复盘，必要时更新流程或规范。

### 12.1 需求简报

```markdown

## 背景

## 目标

## 非目标

## 用户与场景

## 范围

## 约束与依赖

## 验收标准

## 风险与待确认问题

## 负责人、验收者和优先级
```

### 12.2 方案记录

```markdown

## 关联需求

## 已知限制

## 后续任务
```

## 13. 最小强制门禁

任何进入主分支的非临时改动至少必须满足：

1. 有明确目标、范围和可验证的验收标准。
2. 已识别受影响的应用、包、接口、数据和发布边界。
3. 方案和任务规模与风险匹配。
4. 已执行与改动类型匹配的自动化验证。
5. 已完成 Code Review，且没有未处理的阻断性意见。
6. 已确认兼容、迁移、监控和回滚要求。
7. 验收结果、已知限制和后续事项有记录。
